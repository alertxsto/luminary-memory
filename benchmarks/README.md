# Benchmarks

The benchmark has two intentionally separate arms:

1. a deterministic synthetic corpus for pipeline latency smoke tests; and
2. an independently labelled gold set for retrieval, abstention, evidence, and
   scope-isolation checks.

Run both with:

```bash
python3 -m benchmarks.run_benchmarks --n 500 --report /tmp/bench.json
```

To evaluate accuracy against the real embedding model instead of the
deterministic stub:

```bash
python3 -m benchmarks.run_benchmarks --n 500 --engine real --report /tmp/bench-real.json
```

The report records the gold-set SHA-256, configuration, git revision, and the
fact that relevance labels are not generated by the retriever. The default
`gold_micro.jsonl` is a controlled 12-case regression suite, not proof of
superiority over Mem0, Hindsight, or any other provider. A matched competitor
run requires the same corpus, model, extraction budget, answer model, and
metrics.

- Deterministic seed, SQLite by default.
- `--backend sqlite` only for now; pgvector is covered by mocked/integration tests.
- `--gold-set PATH` evaluates another versioned JSONL fixture.
- `--engine fake|real` selects the gold-evaluation engine. `fake` is the
  default and is the only engine ever used for the latency arm, so latency
  numbers stay comparable across releases.
- `--report PATH` writes the complete JSON report.

### Evaluation clock

The fixture stores absolute timestamps, so recall scores would drift as
wall-clock time moves. Fixture timestamps are rebased at load time so the
newest `observed_at` equals run time, preserving relative ages and validity
windows. The original anchor is recorded in
`evaluation.evaluation_clock.anchor`, and the same commit scores the same on any
date.

### Gold quality fields

`recall@10`, `mrr`, `precision@10`, `abstention_accuracy`,
`unsupported_answer_rate`, `cross_scope_leakage`, and per-case results. Two
fields exist specifically so grounding is never confused with relevance:

| Field | Meaning |
|---|---|
| `wrong_hit_rate`, `wrong_hit_rows`, per-case `wrong_hit_ids` | Answer-bearing cases that returned at least one irrelevant row, even when that row carries its own evidence quote. |
| `source_grounded_rate` | Share of returned rows that carry stored-source grounding. **Not** accuracy. |

Reports identify the engine, model, Python/NumPy/Fastembed versions, the
evaluation clock, and `protocol` (`independent_gold_v2`). Fake and real results
are never conflated: `latency_engine` always reads `fake-deterministic`.

Recorded runs live in [`baselines/`](baselines/README.md). Quote those instead
of historical aggregates.

## Two fixtures

| Fixture | Memories | Cases | Use |
|---|---:|---:|---|
| `gold_micro.jsonl` | 12 | 12 | Fast regression suite. Every token is unique to one memory, so it cannot calibrate anything that depends on vocabulary frequency. |
| `gold_extended.jsonl` | 28 | 15 | Realistic store: 16 in-scope background memories make shared vocabulary a real signal. Generated by `build_gold_extended.py`; the micro cases are preserved unchanged. |

`gold_extended.jsonl` is derived, not hand-edited:

```bash
python benchmarks/build_gold_extended.py
```

### Current extended-fixture result

Measured with the real default model. This is deliberately **not** a clean
number — the fixture exposes defects the 12-case set hides:

```
recall@10 0.792   precision@10 0.792   abstention 0.33   wrong_hit 0.08
```

| case | expected | returned | problem |
|---|---|---|---|
| `no_answer_other_user` | abstain | `bg_loadtest-env` | shares only the word "cluster" |
| `no_answer_fingerprint` | abstain | `bg_loadtest-env`, `shared_rule` | same |
| `latest_only` | current deploy facts | `bg_rollback` | correct fact ranks 4th by cosine (0.6775) behind three adjacent rows; not a validity or scope bug |
| `private_wording` | `docs_url` | `docs_url`, `bg_latency-target` | extra unrelated row |

`rule` is **not** in this table. In the larger store, "The release checklist
requires two reviewers before a deploy" is also a correct answer to "What must
happen before release?", so the case lists both ids as relevant. The micro
fixture labels only `shared_rule` because nothing else in its 12-memory store
answers that question; completing the label here is a correctness fix, not a
retrieval failure being relabelled as success.

### How the semantic floor was chosen

`semantic_support_floor()` is the boundary between "answers the question" and
"topically adjacent". It was set from a sweep over both fixtures plus the
release gate, not from a single case:

| floor | micro recall / wrong-hit | extended recall / wrong-hit | release gate |
|---:|---|---|---|
| 0.70 | 0.90 / 0.10 | 0.88 / 0.25 | fail |
| 0.72 | 0.90 / 0.10 | 0.88 / 0.17 | fail |
| 0.73 | 0.70 / 0.10 | 0.79 / 0.17 | fail |
| **0.74** | **0.70 / 0.00** | **0.79 / 0.08** | **pass** |
| 0.78 | 0.70 / 0.00 | 0.75 / 0.08 | pass |

0.74 is the lowest floor that stops the off-topic documentation row from being
returned: its cosine on the exact deploy question is `0.7098`, so 0.70 admitted
it. Higher floors buy nothing — 0.78 keeps the same wrong-hit rate and loses
extended recall — so 0.74 is the operating point.

This deliberately gives up some recall for zero wrong hits. For a memory layer
a wrong answer is worse than an abstention: `preference` and `rule` abstain at
0.74, which is safe, whereas returning a grounded but off-topic URL is not.

Because this fixture is known-red, it is a diagnostic corpus, not a gate. Do
not add it to CI until the failures are resolved; use `gold_micro.jsonl` for
regression and this one to check whether a candidate fix generalises.

## Hindsight-parity benchmark (provider)

`benchmarks/hermes_provider_bench.py` measures the resource + latency profile of the
Hermes memory provider against Hindsight's local_embedded mode:

```bash
python benchmarks/hermes_provider_bench.py --n 5000 --backend sqlite --report /tmp/lum_vs_hindsight.json
```

Measured for luminary (CI-safe, deterministic fake embedding):

- **recall p50/p95** — end-to-end `client.recall()` latency (incl. embedding), fixed query set
- **peak RSS** — max resident set size observed during the run
- **lifecycle duration** — `run_lifecycle()` (TTL cleanup + consolidate + prune) on the same store

Report shape:

```json
{"n": 5000, "backend": "sqlite", "ingest_ms": ..., "recall_latency_ms": {"p50": ..., "p95": ..., "mean": ...}, "lifecycle_ms": ..., "peak_rss_mb": ..., "queries": [...]}
```

### Hindsight reference arm (optional, manual)

Hindsight's local_embedded mode downloads ~200MB of model weights and runs a daemon,
so it is intentionally **not** a CI gate. To record the reference numbers manually:

1. Install Hindsight with local_embedded per its docs.
2. Ingest the same synthetic dataset (`benchmarks/synthetic.py`, `--n 5000`).
3. Run the same fixed query set; record p50/p95 latency and peak RSS.
4. Paste the numbers into the `reference.hindsight_local_embedded` field of the report.

This arm is a resource/latency comparison only. It does not establish that
Luminary is more accurate than Hindsight. Accuracy claims require a matched
independent gold set and the same model/extraction conditions.
